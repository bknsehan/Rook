The Rook Language Guide

A technical specification and comprehensive reference manual for Rook: a modern systems language with 1:1 C ABI compatibility, memory-safe defaults, zero-overhead single inheritance, and dual C/LLVM compilation backends.

Compiler: rokade  |  Target Audience: Developers with prior programming knowledge  |  Fully self-contained.

1. The Rook Philosophy & Prior Art

↑ Top

The systems programming landscape demands both high performance and extreme reliability. For over fifty years, C has been the bedrock of computing, serving as the universal language for operating systems, hardware drivers, embedded microcontrollers, and real-time engines. Almost every software system exposes or consumes the C Application Binary Interface (ABI).

However, programming in traditional C presents well-documented ergonomic and safety hurdles:

  • Header Synchronization: Manually keeping .h header files and .c source files in sync creates unnecessary maintenance overhead and causes subtle linker mismatches.
  • Uninitialized Memory and Bug-Prone Defaults: Uninitialized variables contain arbitrary stack garbage, assignments inside conditional statements (if (x = 5)) silently introduce logic errors, and unchecked pointer operations can trigger undefined behavior.
  • Manual Encapsulation Boilerplate: Standard C lacks native syntax for method calls, inheritance, and tagged unions, requiring repetitive struct nesting and error-prone void pointer casting.

Language Context, Trade-Offs, and Prior Art

Modern languages have approached these systems engineering challenges from different angles. Rook respects the solutions pioneered across the industry while making deliberate trade-offs tailored to its focus:

  • C: Delivers unbeatable ABI ubiquity, hardware transparency, and zero runtime cost. However, it suffers from preprocessor hazards, header duplication, and lack of built-in encapsulation. Rook preserves 100% C ABI compatibility and zero runtime overhead, while eliminating headers via #comprise, enforcing safe variable initialization, and offering clean single inheritance and sum types.
  • C++: Provides powerful abstractions, generic programming, and extensive standard libraries. However, it introduces immense language complexity, slow build times, and non-trivial ABI name mangling that complicates C interoperability. Rook keeps the simplicity and transparent compilation model of C, providing lightweight object methods and defer without template overhead or mangled symbols.
  • Rust: Sets the gold standard for compile-time safety and concurrency via its borrow checker. However, it carries a steep learning curve, strict lifetime annotations, and significant friction when interacting heavily with untyped C memory layouts. Rook prioritizes familiar, lightweight C-style development with pragmatic compile-time guards, letting developers work directly with native C pointers without borrow-checker friction.
  • Zig & Odin: Excel at clean systems ergonomics, explicit memory management, and modern compiler tooling. However, their standalone toolchains and independent ABIs require dedicated bindings to integrate into existing C builds. Rook stays directly inside the C compilation pipeline by transpiling cleanly to standard C, allowing single .rook files to drop into any existing C Makefile or CMake project seamlessly.
  • Go: Popularized productive syntax, fast compilation, and simple concurrency. However, its garbage collection runtime and memory overhead make it unsuitable for bare-metal targets, kernel drivers, and low-latency audio or game engines. Rook operates with zero garbage collection, deterministic memory layouts, and immediate hardware execution.

Rook's Core Strengths

  • Zero-Overhead 1:1 C ABI Parity: Every Rook struct, primitive, and function maps directly to native C, enabling direct calls to libraries like SDL, Raylib, SQLite, or Vulkan without FFI wrappers.
  • Modular Header-Free Imports: Single-file modules imported with #comprise, eliminating the need for separate .h files and include guards.
  • Safer Defaults by Design: Guaranteed zero-initialization for all variables, compile-time bans on assignment in conditions, optional runtime bounds checks (-b), and deterministic defer resource cleanup.
  • Lightweight Abstractions: Single inheritance (object Child : Parent), method syntax with impl, and first-class sum types with pattern matching (match).

What Rook Is Not: Honest Boundaries

To remain fast, lightweight, and completely compatible with standard C, Rook intentionally makes specific trade-offs:

  • No Formal Borrow Checker: Rook does not mathematically prove memory lifetimes at compile time like Rust. You manage memory with pointers, allocators, and arenas.
  • No Garbage Collection: Rook does not automatically collect unreferenced memory. If you require automatic memory management without tracking lifecycles, a managed language like Go or Python is more suitable.
  • Early Ecosystem: Rook's library ecosystem is young compared to long-standing languages, though its direct C interoperability provides immediate access to existing C libraries.
  • LLVM Backend Status: Rokade includes both a C transpiler backend and an LLVM backend. The C backend is stable and production-ready. The LLVM backend is experimental, actively evolving, and not yet as mature as the primary C backend.

Primary Use Cases

  • Systems and Embedded Tools: Compilers, command-line utilities, daemons, and microcontrollers where runtime overhead and garbage collection are unacceptable.
  • Game Engines and Graphics: Low-latency audio, physics, and graphics programming with Raylib, SDL2, OpenGL, or Vulkan.
  • Gradual Modernization of Legacy C: Upgrading brittle C modules to clean, type-safe .rook units without rewriting the surrounding C codebase or build infrastructure.

2.1 Compiler Backends: Pragmatic Realism

Rokade provides two distinct code generation backends, designed with clear real-world trade-offs in mind:

BackendStatusStrengths & Recommended Use
C Backend (Default) Primary & Production-Ready Transpiles .rook code into clean, formatted C99/C11/C23 and invokes host GCC or Clang directly via fork()/execv(). 100% C ABI parity, seamless debugging with standard tools (GDB, LLDB, Valgrind), and zero friction with external C libraries. 2.2 The Lowering Pipeline

  1. Lexing & Parsing: Tokenizes source files and constructs an Abstract Syntax Tree (AST). Recursive module inclusion (#comprise) resolves and deduplicates file imports into a unified compilation unit.
  2. Semantic Analysis (sema.c): Validates type safety, verifies function arity, checks branch exhaustiveness, enforces pointer arithmetic rules, and rejects banned constructs (e.g. assignments in conditions, goto, division by zero).
  3. Code Generation:
    • C Backend (Default): Emits highly readable, formatted C99/C11/C2x code into build/generated/main.c. Every Rook construct maps deterministically to a standard C counterpart.
    • LLVM Backend: Emits LLVM Intermediate Representation (.ll) and drives LLVM target code generators to emit native machine object files (.o) or execute directly via an in-process JIT engine.
  4. Zero-Shell Direct Toolchain Execution: Rokade invokes the host C compiler (gcc or clang) and linker directly using POSIX fork()/execv() (or CreateProcess on Windows). It avoids shell wrappers (sh -c), preventing command-injection attacks and ensuring exact argument propagation.
Transparent Output Inspection
Because Rokade's primary backend generates clean C in build/generated/main.c, you can inspect the generated code at any time with rokade --emit-c src/main.rook. There are no proprietary bytecode formats or obfuscated runtime libraries.

2.3 ABI Parity with C

Rook guarantees 1:1 ABI parity with the host C compiler:

  • Primitive types (int, size_t, float, double, char*) have identical size, alignment, and calling conventions.
  • Rook struct and object types match standard C struct memory layout with identical field offsets and padding.
  • Functions defined in Rook can be called directly from C, and C functions can be called directly from Rook without wrappers or marshaling.

3. Direct Comparison: Standard C vs. Rook

↑ Top

For systems engineers and C programmers evaluating Rook, this chapter provides a direct, comprehensive comparison between standard C and Rook across eight essential architectural and day-to-day programming patterns. Rook is designed to feel immediately natural to C developers while eliminating common failure modes at compile time.

3.1 Modular Code vs. Header Synchronization

In standard C, sharing code between multiple files requires manually maintaining separate header declarations (.h) with preprocessor include guards, and source definitions (.c). Rook uses single-file modules imported with #comprise, and the compiler extracts declarations and prevents symbol collisions automatically.

Feature DimensionStandard CRook
Source Organization Dual-file maintenance: math.h (declarations) and math.c (definitions). Single-file modules: math.rook contains both interface and implementation.
Import Semantics #include "math.h" textually pastes header contents and requires #ifndef guard macros. #comprise math parses module AST once and deduplicates symbols cleanly.
Signature Drift Changing a function signature requires editing both .h and .c, and mismatches cause linker errors. Single source of truth permanently eliminates declaration/definition drift.
Standard C: Header + Implementation
// math.h
#ifndef MATH_H
#define MATH_H
int add(int a, int b);
#endif

// math.c
#include "math.h"
int add(int a, int b) { return a + b; }
Rook: Clean Modular Import
// src/math.rook
int add(int a, int b) {
    return a + b;
}

// src/main.rook
#comprise math
#include <stdio.h>

int main() {
    printf("Sum: %d
", add(10, 20));
    return 0;
}

3.2 Variable Initialization & Stack Safety

In standard C, local variables declared without an initializer inherit whatever arbitrary bit patterns existed on the CPU stack. Reading an uninitialized variable is undefined behavior (UB) and a frequent source of security vulnerabilities.

ConditionStandard CRook
Uninitialized Local int x; has indeterminate value (stack garbage). int x; is guaranteed zero-initialized (lowered to int x = {0};).
Array Initialization int arr[100]; contains 100 garbage integers. int arr[100]; is guaranteed zeroed out at declaration.
Struct Initialization Point p; has uninitialized padding and fields. Point p; has all fields cleanly initialized to zero.
Standard C (Dangerous Stack Garbage)
// Standard C: Undefined Behavior
int health; // Contains garbage stack data (e.g. -1074823904)
if (health > 0) { // Unpredictable branch!
    take_action();
}
Rook (Guaranteed Zero-Init)
// Rook: Deterministic 0 initialization
int health; // Guaranteed to be 0
if (health > 0) { // Deterministic: branch is never taken
    take_action();
}

3.3 Compile-Time Ban on Assignment in Conditions

In standard C, mistakenly typing a single equals sign (=) instead of a double equals sign (==) inside an if condition silently overwrites the variable and evaluates the assigned value as a truth condition. Rook detects assignments inside conditionals at compile time and immediately halts compilation with an actionable diagnostic.

Standard C (Dangerous Silent Mutation)
// Standard C: Compiles silently with a warning (or none), mutating state!
if (status = 0) { // Bug: status is set to 0, block never executes
    handle_success();
}
Rook (Compile-Time Enforcement)
// Rook: Compile-time error!
if (status = 0) { // Compile Error: assignment in condition is banned
    handle_success();
}
// Fix: use equality operator ==
if (status == 0) {
    handle_success();
}

3.4 Encapsulation & Single Inheritance

Standard C has no native concept of methods or object inheritance, so programmers must manually nest structs and cast pointers, losing type safety. Rook introduces the object keyword and impl blocks, producing zero runtime overhead with 1:1 C struct compatibility.

Standard C: Emulated Inheritance
// Standard C: Manual struct nesting & pointer casts
typedef struct { float x, y; } Point;
typedef struct { Point base; float radius; } Circle;

void point_move(Point* p, float dx, float dy) { p->x += dx; p->y += dy; }

Circle c = { {10.0f, 20.0f}, 5.0f };
point_move((Point*)&c, 1.0f, 2.0f); // Manual, unverified cast
Rook: Clean Single Inheritance
// Rook: First-class object inheritance with zero overhead
object Point {
    x: float;
    y: float;
}

object Circle : Point {
    radius: float;
}

impl Point {
    void move(Point* self, float dx, float dy) {
        self.x += dx;
        self.y += dy;
    }
}

Circle c = Circle{ x: 10.0f, y: 20.0f, radius: 5.0f };
c.move(1.0f, 2.0f); // Type-safe, calls point_move(&c._base, 1.0f, 2.0f)

3.5 Tagged Unions & Algebraic Sum Types

Representing data that can take one of several shapes in standard C requires an enum tag, a union, and disciplined manual bookkeeping. Rook provides first-class sum types with compile-time pattern matching.

Rook: Algebraic Sum Types & Pattern Matching
sum NetworkEvent {
    Connected{ client_id: int; ip: const char*; };
    DataReceived{ client_id: int; bytes: int; };
    Disconnected{ client_id: int; };
}

void handle_event(NetworkEvent* ev) {
    match (*ev) {
        Connected(c) => printf("Client %d connected from %s
", c.client_id, c.ip),
        DataReceived(d) => printf("Client %d sent %d bytes
", d.client_id, d.bytes),
        Disconnected(q) => printf("Client %d disconnected
", q.client_id),
    }
}

3.6 Resource Management: goto cleanup; vs. defer

Robust error handling in C typically requires manual cleanup labels and goto ladders. Rook provides defer, which schedules execution at the end of the enclosing scope in Last-In, First-Out (LIFO) order.

Standard C: Error Cleanup Ladder
// Standard C: goto cleanup ladder
int process(const char* path) {
    FILE* fp = fopen(path, "r");
    if (!fp) return -1;
    char* buf = malloc(1024);
    if (!buf) { fclose(fp); return -2; }
    
    int ret = 0;
    if (do_work(fp, buf) < 0) { ret = -3; goto cleanup; }
    
cleanup:
    free(buf);
    fclose(fp);
    return ret;
}
Rook: Clean defer Cleanup
// Rook: Deterministic LIFO defer
int process(const char* path) {
    FILE* fp = fopen(path, "r");
    if (!fp) return -1;
    defer fclose(fp); // Guaranteed cleanup on any return path

    char* buf = (char*)malloc(1024);
    if (!buf) return -2;
    defer free(buf); // Runs before fclose(fp)

    if (do_work(fp, buf) < 0) return -3;
    return 0;
}

3.7 Pointer Safety & Explicit Arithmetic

Standard C allows pointer arithmetic on untyped void* pointers via compiler extensions. Rook enforces strict type checking: arithmetic on void* is banned at compile time, requiring explicit casts to byte pointers (char* or u8*).

3.8 Toolchain, Build System & Execution Security

4. Mental Model & Memory Semantics

↑ Top

Unlike languages that impose managed runtimes, tracing garbage collection, or complex reference counting, Rook adopts the flat, transparent memory model of C, augmented by deterministic safety guarantees.

4.1 The Stack & Automatic Zero-Initialization

In standard C, uninitialized local stack variables contain arbitrary leftover memory contents, leading to undefined behavior and security exploits:

Standard C (Dangerous)
// Standard C: Undefined Behavior
void compute(void) {
    int counter;      // Stack garbage! Could be 0, could be -19827312
    if (ready) counter++; // Undefined behavior
}

In Rook, every local variable declaration without an initializer is guaranteed to be zero-initialized at compile time:

Rook (Safe by Default)
int compute() {
    int counter; // Rokade lowers this to: int counter = {0};
    printf("%d\n", counter); // Guaranteed to print 0
    return 0;
}

4.2 The Heap & Deterministic Lifecycle

Heap memory in Rook is explicit. You allocate memory using standard functions (such as malloc / calloc) or specialized memory structures like std/mem bump arenas. Rook provides no background garbage collector; heap allocations live until explicitly reclaimed.

To eliminate memory leaks and ensure resources are properly released along all code paths (including early returns and error conditions), Rook introduces the defer statement:

Deterministic Scope Cleanup
#include <stdio.h>
#include <stdlib.h>

int process_file(const char* path) {
    FILE* fp = fopen(path, "rb");
    if (!fp) return -1;
    defer fclose(fp); // Guaranteed to execute on any function return

    char* buffer = (char*)malloc(4096);
    if (!buffer) return -2;
    defer free(buffer); // Executes before fclose(fp)

    // Read and process data...
    return 0; // Both buffer and fp are automatically cleaned up here
}

4.3 Object Memory Layout

Rook's object system provides single inheritance with zero runtime overhead. An object inheriting from a base type embeds the base struct as its first member (struct Base _base;). There are no virtual method tables (vtables), no runtime type indicators, and no pointer indirections. A pointer to a derived object can be safely cast and passed to any function expecting a pointer to its base type.

7.1 Declaration Forms in v0.4.1

8. Pointers & Pointer Safety

↑ Top

Pointers are fundamental to systems programming. Rook preserves direct pointer access and low-level memory manipulation, but eliminates syntactical confusion and enforces strict compile-time safety checks.

8.1 Standardized Postfix Notation

In standard C, whitespace variability creates confusing pointer declarations (e.g. int *p vs int* p). Rook standardizes strictly on postfix notation:

Valid Pointer Syntax
int* ptr = &x;     // Correct in Rook
const char* name;  // Correct in Rook
Prefix Pointer Syntax Banned
Prefix notation like *int ptr; is strictly rejected by the Rook parser: 
error: invalid pointer syntax '*Type'; Rook standardizes on postfix 'Type*'

8.2 Pointer Operations

Address-of & Dereference
#include <stdio.h>

void swap(int* a, int* b) {
    int temp = *a;
    *a = *b;
    *b = temp;
}

int main() {
    int x = 10;
    int y = 20;
    swap(&x, &y);
    printf("x=%d, y=%d\n", x, y); // x=20, y=10
    return 0;
}

8.3 Enforced Pointer Arithmetic Rules

Rook's semantic analyzer enforces rigorous safety rules around pointer calculations:

  • Typed Pointer Offsets: Adding or subtracting integers from typed pointers (p + 1, p++) is permitted and steps memory by sizeof(*p).
  • Prohibition on void* Arithmetic: In C, GCC permits arithmetic on void* as an extension, treating sizeof(void) as 1. Rook considers this dangerous and rejects it at compile time:
    void* Arithmetic Enforcement
    void* buf = get_buffer();
// COMPILE ERROR: pointer arithmetic on 'void*' is invalid
void* next = buf + 8; 

// CORRECT: cast explicitly to a byte-oriented pointer
uint8_t* byte_ptr = (uint8_t*)buf;
uint8_t* next_byte = byte_ptr + 8; // Valid
  • Prohibition of Non-Additive Operations: Multiplying, dividing, modulo-ing, or performing bitwise shifts on pointers is illegal and rejected at compile time:
    Illegal Pointer Math Banned
    int* p = &x;
p = p * 2; // COMPILE ERROR: invalid operand to binary operator
p = p & 0xFF; // COMPILE ERROR: invalid operand to binary operator

9. Control Flow & Branching

↑ Top

Rook provides structured control flow primitives familiar to C developers, with compile-time enforcements that prevent classic logical errors.

9.1 Conditionals: if / else

Standard Conditional
if (status == 200) {
    printf("OK\n");
} else if (status >= 400 && status < 500) {
    printf("Client Error\n");
} else {
    printf("Other\n");
}
Assignment in Condition Strictly Banned
One of the most frequent bugs in C is accidentally typing if (x = 5) instead of if (x == 5). Rook's semantic analyzer recursively inspects condition expressions (stripping parentheses) and rejects assignment expressions in:
  • if (cond)
  • while (cond)
  • for (...; cond; ...)
  • switch (cond)
  • Ternary operators: (cond) ? a : b
error: assignment used as condition; did you mean '=='?

9.2 Iteration: while, do-while, for, and for-in

Looping Constructs
// 1. Classic while loop
int i = 0;
while (i < 5) {
    i++;
}

// 2. Standard C-style for loop
for (int idx = 0; idx < 10; idx++) {
    if (idx == 3) continue;
    if (idx == 8) break;
}

// 3. Range-based for-in loop
for score in [95, 88, 72, 100] {
    printf("score: %d\n", score);
}

9.3 Scalar Branching: C switch

For scalar dispatch (integers and enums) using jump tables, Rook supports standard C switch:

Classic C switch
switch (opcode) {
    case 1:
        execute_add();
        break;
    case 2:
        execute_sub();
        break;
    default:
        handle_unknown();
        break;
}
Consolidation of switch and match in v0.4.1
Earlier builds contained an experimental arrow syntax inside switch (case 1 -> action();). In Rook v0.4.1, arrow switch was removed to keep switch dedicated exclusively to traditional C semantics. All modern pattern matching, destructuring, and expression branching are consolidated into the match construct (see Chapter 12).

9.4 Prohibition of goto

Rook explicitly bans the goto keyword. All control flow must be expressed via structured constructs (if, while, for, switch, match, break, continue, and return).

10.2 Compile-Time Enforcements

  • Strict Return Validation: Any non-void function must return an appropriate value across all execution paths. A function falling through without a return triggers a compile-time error.
  • Arity & Type Verification: Function calls are statically verified against declarations. Calling a function with missing or extraneous arguments fails immediately.
  • Top-Level Scope Enforcement: Nested function declarations (defining a function inside another function body) are illegal and rejected.

12. Objects, Methods & Single Inheritance

↑ Top

Rook provides an elegant object model featuring single inheritance and method dispatch with zero runtime cost. Unlike C++, Rook introduces no virtual method tables (vtables), no runtime type information (RTTI), and no hidden pointer indirection.

12.1 The object Keyword

An object defines a record type that can participate in single inheritance:

Object Inheritance
object Entity {
    int id;
    float x;
    float y;
}

// Player inherits all fields from Entity
object Player : Entity {
    int health;
    const char* username;
}

12.2 Memory Lowering & ABI Parity

When Rook transpiles object Player : Entity, it lowers the inheritance hierarchy by embedding the base type as the first struct member named _base:

Lowered C Struct Representation
// Generated C representation
typedef struct Entity {
    int id;
    float x;
    float y;
} Entity;

typedef struct Player {
    struct Entity _base; // Embedded at offset 0
    int health;
    const char* username;
} Player;

Because _base is located at offset 0 of Player, a pointer to Player is binary-compatible with a pointer to Entity under standard C ABI rules. Any function accepting Entity* can receive (Entity*)player_ptr without overhead.

12.3 Method Dispatch with impl

Methods are defined outside the struct definition using impl blocks:

Methods & Inheritance in Action
#include <stdio.h>

object Shape {
    float x;
    float y;
}

impl Shape {
    void translate(Shape* self, float dx, float dy) {
        self->x += dx;
        self->y += dy;
    }
}

object Circle : Shape {
    float radius;
}

impl Circle {
    void describe(self) { // 'self' shorthand automatically types to Circle*
        printf("Circle at (%.1f, %.1f) with radius %.1f\n", self.x, self.y, self.radius);
    }
}

int main() {
    // Flat initialization across parent and child fields
    let c = Circle{ x: 10.0f, y: 15.0f, radius: 5.0f };
    
    // Call method on derived type
    c.describe();

    // Call inherited method from base type
    c.translate(5.0f, -5.0f);
    c.describe();
    return 0;
}
Zero-Cost Method Lowering
Method invocations such as c.describe() lower to direct C function calls: Circle_describe(&c). Inherited calls like c.translate(...) automatically lower to Shape_translate(&c._base, ...). Dispatch is 100% static, inlined by the C compiler, and incurs zero vtable indirection.

13.2 Sum Types (Tagged Unions)

A sum type represents a value that can hold one of several distinct variant shapes. Variants may be unit variants (bearing no payload) or data variants:

Sum Type Declaration
sum Node {
    Leaf { value: int; };
    Branch { left: Node*; right: Node*; };
    Empty;
}

In memory, Rokade lowers a sum type into a C struct containing an integer discriminator tag and an anonymous union storing the variant payloads:

Lowered Tagged Union
typedef struct Node {
    int tag; // Identifies which variant is currently active
    union {
        struct { int value; } Leaf;
        struct { struct Node* left; struct Node* right; } Branch;
    };
} Node;

13.3 Pattern Matching: match

The match construct provides comprehensive destructuring for sum types, enums, and scalar values. It is supported in both statement and expression forms.

Statement Form:

Statement Pattern Match
void print_node(Node* n) {
    match (*n) {
        Leaf { value } => printf("Leaf: %d\n", value),
        Branch { left, right } => printf("Branch\n"),
        Empty => printf("Empty\n"),
        _ => printf("Unknown\n")
    }
}

Expression Form:

Expression Pattern Match
sum Shape {
    Circle { radius: float; };
    Rectangle { width: float; height: float; };
    Point;
}

float calculate_area(Shape s) {
    return match (s) {
        Circle { radius } => 3.14159f * radius * radius,
        Rectangle { width, height } => width * height,
        Point => 0.0f,
        _ => 0.0f
    };
}

13.4 Instantiating Sum Types & Methods with impl

To instantiate a sum type, specify the sum type name as the variable type (or use explicit type annotation with let) and provide the variant constructor:

Sum Type Instantiation & Methods
#include <stdio.h>

    Circle { r: float; };
    Rect { w: float; h: float; };
    Point;
}

// Methods can be attached to sum types via impl

            Circle { r }  => 3.14159f * r * r,

            Point         => 0.0f,
            _             => 0.0f,
        };
    }
}

int main() {
    Shape a = Circle{ r: 2.0f };
    Shape b = Rect{ w: 3.0f, h: 4.0f };
    Shape c = Point;

}

14. Deterministic Cleanup: defer

↑ Top

Manual resource cleanup is the primary source of memory leaks and descriptor exhaustion in C. Rook solves this with the defer statement, providing deterministic scope-based resource reclamation.

14.1 defer Mechanics

When defer <stmt>; is encountered, the deferred statement is scheduled to run when the surrounding lexical scope terminates. Multiple deferred statements execute in Last-In, First-Out (LIFO) order (stack unwinding):

LIFO Execution Order
#include <stdio.h>

void trace_lifo() {
    defer printf("First deferred (runs last)\n");
    defer printf("Second deferred (runs middle)\n");
    printf("Function body execution\n");
    defer printf("Third deferred (runs first)\n");
}

int main() {
    trace_lifo();
    return 0;
}

Output:

Execution Output
Function body execution
Third deferred (runs first)
Second deferred (runs middle)
First deferred (runs last)

14.2 Resource Pairing Idioms

Place defer immediately after acquiring any resource to guarantee deallocation, regardless of whether the function returns early or encounters an error:

Safe Resource Management
#include <stdio.h>
#include <stdlib.h>

int process_data(const char* filename) {
    FILE* f = fopen(filename, "r");
    if (!f) return -1;
    defer fclose(f); // Guaranteed closure

    int* data = (int*)malloc(1000 * sizeof(int));
    if (!data) return -2; // f is closed automatically!
    defer free(data);     // Guaranteed deallocation

    // Process file...
    if (read_error()) {
        return -3; // Both data is freed and f is closed!
    }

    return 0; // Both data is freed and f is closed!
}

Module 1: How Computers Actually Work

↑ Top

Welcome to programming! Before writing a single line of code, it helps immensely to have a clear picture of what a computer actually is and how it follows instructions. You don't need an engineering degree to understand this,just a few simple mental models.

1.1 The Physical Triumvirate: CPU, RAM, and Storage

Every computer,from the phone in your pocket to massive supercomputers in data centers,relies on three core physical components working in harmony:

The Storage (SSD / Hard Drive)
Permanent Library
Large, durable, but slow
➔
The RAM (Working Memory)
Kitchen Countertop
Blazing fast, temporary scratchpad
➔
The CPU (The Processor)
The Chef / Calculator
Executes billions of simple steps per second
  • The Storage (SSD or Hard Drive): Think of this as a permanent bookshelf or filing cabinet. When you turn your computer off, everything stored here remains safe. Your operating system, games, and code files live here. However, storage is relatively slow for the CPU to interact with directly.
  • RAM (Random Access Memory): Think of this as your active kitchen countertop or desk scratchpad. When you launch an application or compile code, the program is copied from storage into RAM. The CPU can read and write data in RAM in nanoseconds. However, RAM is volatile: when you shut down the computer, everything on the countertop is wiped clean.
  • The CPU (Central Processing Unit): Think of this as a hyper-fast, literal-minded calculator or chef. The CPU does not "think" or understand human nuance. It simply fetches an instruction from RAM, executes it (like adding two numbers or checking if a number is zero), and moves to the next instruction,billions of times per second.

1.2 Bits and Bytes: The Alphabet of Hardware

Computers do not speak English, Spanish, or Indonesian. At the microscopic hardware level, computer chips consist of billions of microscopic transistors that act like light switches:

  • A switch can only be in one of two states: OFF (0) or ON (1).
  • A single 0 or 1 is called a bit (short for binary digit).
  • Because a single bit can only represent two states, computers group bits into sets of eight. A group of 8 bits is called a byte.
💡 Why 8 Bits = 1 Byte?
With 8 bits, you can create 256 unique combinations of 0s and 1s (from 00000000 to 11111111). In decimal numbers, that covers 0 through 255. This was historically enough to assign a unique number to every English letter (A-Z, a-z), digit (0-9), and punctuation symbol in the standard ASCII character table!

1.3 Source Code vs. Machine Code: What is a Compiler?

Humans cannot reasonably write billions of 1s and 0s by hand (called machine code). Instead, we write human-readable text called source code using a programming language like Rook or C.

Because the CPU cannot directly run human text, we use a special tool called a compiler (such as rokade):

  1. You write source code: Clear, human-readable instructions saved in a text file (e.g. main.rook).
  2. The compiler inspects your code: It checks for grammar errors, verifies data types, and ensures safety rules are respected.
  3. The compiler emits machine code: It translates your human instructions into raw binary instructions that your CPU can execute directly at maximum speed.

1.4 High-Level vs. Low-Level Languages

Not all programming languages speak at the same altitude. We broadly divide them into two categories:

  • Low-Level Languages sit very close to the hardware. They give you direct control over memory, CPU registers, and individual bytes. The closer you are to the machine, the faster your code can run, but the more details you have to manage yourself. Examples include Assembly and C.
  • High-Level Languages sit further from the hardware and handle many details for you automatically, such as memory management, type conversions, and common data structures. They let you think in human-friendly concepts (lists, objects, events) rather than memory addresses. Examples include Python, JavaScript, and Ruby.

Rook occupies the low-to-middle ground: it gives you C-level control when you need it, but removes common sources of mistakes that low-level C programs suffer from, such as implicit type coercions and uninitialized memory.

1.5 Compiled, Interpreted, and Transpiled Languages

There is more than one way to turn source code into something a computer can run. The three most common approaches are:

ApproachWhat it doesWhen it happensExamples
Compiled A compiler reads your source code once, checks it for errors, and produces a native binary file (an .exe on Windows, or no extension on Linux/macOS). That binary runs directly on the CPU with no extra tools needed. Once, before you run the program C, C++, Rook, Rust, Go
Interpreted An interpreter reads your source code line by line and executes each instruction on the spot. There is no separate compile step, but an interpreter must be installed on every machine that runs your code. Every time the program runs Python, Ruby, Bash
Transpiled A transpiler converts source code in one language into equivalent source code in another language, which is then compiled or interpreted normally. The output is human-readable code, not machine code. Once, producing another source file TypeScript (to JS), CoffeeScript (to JS), Sass (to CSS)
Where does Rook fit?
Rook is a compiled language. The rokade compiler reads your .rook files, checks them thoroughly for errors, and produces either a native binary (via a C backend) or LLVM IR (via the LLVM backend). The result runs directly on the CPU without any runtime interpreter.
Key Takeaways of Module 1
  • The CPU is the brain/calculator, RAM is the fast temporary workspace, and Storage is the permanent library.
  • All computer data ultimately consists of bits (0s and 1s) and bytes (groups of 8 bits).
  • Source code is what humans write, machine code is what the CPU executes.
  • A compiler translates your source code into a fast native binary once, before the program runs.
  • Low-level languages give hardware control, high-level languages abstract the details away. Rook sits in between.
  • Compiled languages produce binaries, interpreted languages use a runtime, transpiled languages convert to another source language.

Every programmer's journey begins with a sacred tradition: writing a program that prints the words "Hello, World!" to your screen. Let's look at the complete code, and then dissect every single character so you understand why it is there.

2.1 Line-by-Line Breakdown

  1. #include <stdio.h>
    Programs rarely start from scratch. Standard libraries provide pre-built tools for common tasks. Here, stdio.h stands for Standard Input/Output. Including this tells the compiler: "Please let me borrow the standard tools for reading from the keyboard and writing text to the terminal."
  2. int main()
    This is the official front door of your program. When your operating system (Linux, Windows, or macOS) starts your application, it specifically searches for a function named main to begin execution. The word int before main means that when the program finishes, it will hand back a whole integer number (an exit code) to the operating system.
  3. The Curly Braces { ... }
    In Rook and C, curly braces define a block of code. Everything between the opening { and the closing } belongs to the main function. Think of it like the walls of a room where the work happens.
  4. printf("Hello, World!\n");
    printf stands for Print Formatted. It takes the text inside the quotation marks and displays it on your terminal screen. Notice the funny characters \n at the end: this is an escape sequence that tells the computer to press the "Enter" key and move to a fresh new line.
  5. The Semicolon ;
    In English, every complete sentence ends with a period. In programming, every complete instruction (statement) ends with a semicolon. Forgetting a semicolon is like writing a run-on sentence without punctuation, the compiler won't know where one thought ends and the next begins.
  6. return 0;
    This is your program telling the operating system: "I have finished all my work, and everything went successfully without any errors!" In computing convention, a return code of 0 signifies success, while non-zero numbers (like 1, -1, or 404) signify various error codes.

Module 3: Storing Information: Variables and Types

↑ Top

Programs are not static text, they exist to process information. To do that, a program needs a way to remember numbers, words, and choices. We store information using variables.

3.1 The Labeled Storage Box Analogy

Imagine your computer's RAM as a vast warehouse. A variable is like a sturdy cardboard box with a name tag written on the outside:

  • The Variable Name (Identifier): The name written on the box (e.g. player_score or age).
  • The Data Type: The specific shape of the box, which determines what kind of items can fit inside (e.g. integers only, or decimal numbers only).
  • The Value: The actual item currently sitting inside the box (e.g. 100).

3.2 Fundamental Data Types

Computers handle different kinds of information differently. Storing someone's age is very different from storing their bank account balance or their name. Here are the core data types you will use every day:

Here is how you create and use variables in Rook:

#include <stdio.h>

  • A variable is a named storage location in memory that holds a specific type of data.
  • int is for whole numbers, float for decimals, char for single characters, bool for true/false.
  • Use = to assign or update a value inside a variable box.

Module 4: Doing Math & Making Comparisons

↑ Top

Once you have variables, you want to perform calculations and make comparisons. In programming, we do this using operators.

4.1 Basic Arithmetic Operators

You already know most of these from middle school math:

  • + (Addition): 10 + 5 results in 15
  • - (Subtraction): 10 - 5 results in 5
  • * (Multiplication): 10 * 5 results in 50
  • / (Division): 10 / 5 results in 2
  • % (Modulo / Remainder): 10 % 3 results in 1 (because 3 goes into 10 three times with 1 left over).
⚠️ The Integer Division Surprise!
What happens if you divide 7 / 2 using integers? In math class, the answer is 3.5. But because both 7 and 2 are int, the computer performs integer division: it throws away the decimal remainder and gives you 3! If you want the decimal 3.5, at least one of the numbers must be a decimal: 7.0f / 2.0f.

4.2 Comparison Operators (Asking Questions)

Computers make decisions by testing whether something is true or false:

  • == (Is Equal To?): x == 5 (Notice the double equals! Single = assigns a value, double == compares values).
  • != (Is NOT Equal To?): x != 5 (True if x is anything other than 5).
  • > and < (Greater than / Less than): score > 100
  • >= and <= (Greater than or equal / Less than or equal): age >= 18

4.3 Boolean Logic: Combining Conditions

Often you need to check multiple conditions at the same time:

  • Logical AND (&&): Both conditions must be true.
    Analogy: To ride the roller coaster, you must be tall enough AND have a ticket. If either is missing, you cannot ride.
  • Logical OR (||): At least one condition must be true.
    Analogy: You get a discount if it is Sunday OR you are a student. If either is true, you get the discount.
  • Logical NOT (!): Flips true to false, and false to true.
    Analogy: !is_raining means "it is NOT raining".
Operators in Action
#include <stdio.h>

int main() {
    int age = 20;
    bool has_id = true;

    // Both must be true
    if (age >= 18 && has_id) {
        printf("Access granted: adult with ID.\n");
    }

    // Remainder calculation
    int items = 14;
    int pack_size = 4;
    int leftover = items % pack_size;
    printf("Leftover items: %d\n", leftover); // Prints 2

    return 0;
}
Key Takeaways of Module 4
  • Integer division discards decimals, use floats when you need fractions.
  • Use == to compare values, and = to assign values.
  • && means AND (both true), || means OR (either true), ! means NOT (invert).

Module 5: Making Choices: Control Flow

↑ Top

If code only executed straight down from top to bottom, programs would be completely inflexible. To build intelligent software, we need the computer to make decisions: "If the password is correct, log the user in, otherwise, show an error message." We call this control flow.

5.1 The if, else if, and else Construct

Think of an if statement as a fork in the road. The computer evaluates a condition inside parentheses: if the condition is true, it takes the first path, otherwise, it skips ahead.

Grade Evaluation Branching
#include <stdio.h>

int main() {
    int score = 85;

    if (score >= 90) {
        printf("Grade: A - Outstanding!\n");
    } else if (score >= 80) {
        printf("Grade: B - Great job!\n");
    } else if (score >= 70) {
        printf("Grade: C - Satisfactory.\n");
    } else {
        printf("Grade: F - Needs improvement.\n");
    }

    return 0;
}

How the computer evaluates this:

  1. It checks score >= 90. Since 85 is not >= 90, it moves to the next branch.
  2. It checks score >= 80. Since 85 is >= 80, this condition is true!
  3. It runs the block printing "Grade: B", and then skips all remaining branches completely!

5.2 Banned Assignment in Conditions

One of the most catastrophic bugs in old C code was accidentally writing if (score = 100) instead of if (score == 100). In C, that overwrote the score to 100 and ran the block! In Rook, the compiler checks your code and strictly refuses to compile if you put an assignment inside an if condition, protecting you from subtle bugs.

Key Takeaways of Module 5
  • Use if to execute code only when a condition is met.
  • Use else if to test alternative conditions, and else as a final catch-all.
  • Only the first matching branch in an if/else if chain is executed.

Module 6: Repetition: Automating with Loops

↑ Top

Humans get bored and make mistakes when performing the same task over and over again. Computers, on the other hand, can repeat an operation a billion times with flawless precision. To repeat code, we use loops.

6.1 The while Loop: Repeat While Condition is True

A while loop checks a condition. As long as that condition remains true, it keeps executing its code block:

Countdown with a while Loop
#include <stdio.h>

int main() {
    int countdown = 5;

    while (countdown > 0) {
        printf("%d...\n", countdown);
        countdown = countdown - 1; // Decrement countdown
    }

    printf("Blastoff!\n");
    return 0;
}
⚠️ Beware the Infinite Loop!
If you forget to change countdown inside the loop (e.g. leaving out countdown = countdown - 1;), the condition countdown > 0 will stay true forever! Your program will freeze in an infinite loop. Always ensure your loop has progress toward termination.

6.2 The for Loop: The Counting Specialist

When you know exactly how many times you want to repeat something (like counting from 1 to 10), a for loop is cleaner because it bundles the starting count, the condition, and the step into one line:

Counting with a for Loop
#include <stdio.h>

int main() {
    // for (start; condition; step)
    for (int i = 1; i <= 5; i++) {
        printf("Iteration number: %d\n", i);
    }
    return 0;
}
  • int i = 1;: Runs once at the very beginning to initialize the counter.
  • i <= 5;: Checked before every iteration. If false, the loop ends.
  • i++: Shorthand for i = i + 1. Runs after every iteration to increment the counter.

6.3 Controlling Loops: break and continue

  • break: Immediately exits the loop, skipping any remaining cycles.
  • continue: Immediately stops the current iteration and jumps directly to the next cycle.
Key Takeaways of Module 6
  • Loops automate repetitive work without copy-pasting code.
  • Use while when you don't know in advance how many repetitions you will need.
  • Use for when counting or iterating a known number of times.
  • Always ensure the loop condition eventually becomes false to avoid freezing in an infinite loop.

Module 7: Functions: Reusable Building Blocks

↑ Top

As programs grow, writing all your logic inside main() becomes messy and unmaintainable. To organize software, we divide code into small, named, reusable pieces called functions.

7.1 The Recipe & Kitchen Appliance Analogy

Think of a function as an appliance, like a blender or toaster:

  • Inputs (Parameters): What you feed into the machine (e.g. slices of bread).
  • The Work (Function Body): What happens inside (heating the coils for 2 minutes).
  • Output (Return Value): What comes out of the machine (warm toast).
Creating and Calling Functions
#include <stdio.h>

// A function that takes two integers, adds them, and returns the result
int add(int a, int b) {
    return a + b;
}

// A function that doesn't return anything (void)
void greet(const char* name) {
    printf("Welcome to Rook, %s!\n", name);
}

int main() {
    // Calling our functions
    greet("Alice");
    greet("Bob");

    int sum = add(15, 25);
    printf("15 + 25 = %d\n", sum);

}

7.2 Variable Scope: Where Variables Live and Die

Variables created inside a function are local to that function. They are born when the function begins running, and they are completely destroyed when the function finishes. A function cannot see or accidentally change local variables inside another function.

Key Takeaways of Module 7
  • Functions break large programs into small, readable, testable, and reusable blocks.
  • Parameters are inputs passed into the function, and the return statement sends an output back.
  • Functions with no return value use void.
  • Local variables only exist inside their own function, preventing unintended side effects.

Module 8: Grouping Data: Structures

↑ Top

In the real world, things are rarely single numbers. A person has a name, age, and height. A car has a make, model, year, and fuel level. Storing these as loose, disconnected variables (like car1_year, car2_year, car3_year) quickly creates chaos. In programming, we bundle related variables together using a struct (short for structure).

8.1 Defining and Creating a Struct

A struct is like designing your own custom data blueprint:

Using Structs to Model Data
#include <stdio.h>

// Define our custom blueprint
struct Player {
    name: const char*;
    health: int;
    score: int;
};

int main() {
    // Create an instance of Player and initialize its fields
    Player hero = Player{
        name: "Knight Arthur",
        health: 100,
        score: 0
    };

    // Access fields using the dot (.) operator
    printf("Player: %s\n", hero.name);
    printf("Health: %d HP\n", hero.health);

    // Modify a field
    hero.score += 500;
    printf("New Score: %d points\n", hero.score);

    return 0;
}

Notice how clean this is: hero is a single unified package containing all the state for Arthur. If you need a second player, you just declare Player villain = Player{ ... };.

Key Takeaways of Module 8
  • A struct lets you create custom data types that group related fields together.
  • Use designated initializers (Player{ name: "Arthur", ... }) to set field values clearly.
  • Use the dot operator (player.health) to read or update individual fields.

Module 9: Demystifying Memory: Pointers

↑ Top

Pointers have a scary reputation among programming students. But once you learn the fundamental real-world analogy, pointers are surprisingly simple and intuitive.

9.1 The House vs. The Street Address Analogy

Imagine a long residential street where every house has a unique number painted on the curb (like 100 Main St, 102 Main St, 104 Main St):

  • The Variable: The physical house itself, containing furniture, people, and rooms (the data).
  • The Pointer: A small slip of paper with the address of the house written on it.

The slip of paper is not the house! It is tiny and lightweight, but if you look at the address written on it, you can walk down the street to the house and see what is inside.

9.2 The Two Essential Operators: & and *

  1. Address-of Operator (&): "What is the street address of this variable?"
    If x is a variable, &x gives you the memory address where x lives in RAM.
  2. Dereference Operator (*): "Go to the house at this address and look/change what is inside."
    If ptr holds the address of x, then *ptr reaches into that house!
Pointers in Action
#include <stdio.h>

int main() {
    int gold = 50;       // A house containing 50 gold pieces
    int* ptr = &gold;    // A paper holding the memory address of gold

    printf("Value of gold: %d\n", gold);
    printf("Memory address of gold: %p\n", (void*)ptr);

    // Reach into the house using the pointer and change the gold!
    *ptr = 100;

    printf("Updated gold: %d\n", gold); // Now prints 100!
    return 0;
}

9.3 Why Do We Need Pointers?

If you already have the variable, why bother writing down its address?

  • Modifying variables inside functions: When you pass a variable to a function, the computer usually makes a copy (pass-by-value). If the function modifies its copy, your original variable remains unchanged. But if you pass a pointer (the address), the function can reach back into your original memory and update it directly!
  • Efficiency: If you have a huge struct holding 1,000 game objects, copying it takes time and RAM. Passing a pointer to that struct only copies an 8-byte address, which takes less than a nanosecond!

9.4 What is a NULL Pointer?

A null pointer is a slip of paper with address 0 (nowhere). If you try to dereference a null pointer (knocking on a door at an address that does not exist), the operating system immediately protects itself by terminating your program with a segmentation fault (crash). Always make sure a pointer points to valid memory before dereferencing it.

Key Takeaways of Module 9
  • A variable holds data, while a pointer holds the memory address where data lives.
  • &x gets the address of x.
  • *ptr accesses or modifies the value at the address stored in ptr.
  • Pointers allow functions to modify caller data and pass large structures with zero copy overhead.

Module 10: Working with Lists: Arrays

↑ Top

What if you need to store the high scores of 100 players, or the temperature readings for every day of the year? Creating 365 separate variables would be unbearable. To store an ordered collection of items of the same type, we use an array.

10.1 The Row of Lockers Analogy

Think of an array as a straight row of identical, numbered metal lockers in a school hallway:

  • All lockers in the row hold the same kind of thing (e.g. all hold integers).
  • The lockers sit side-by-side in memory in a continuous sequence.

10.2 Why Do Programmers Start Counting at 0?

In programming, array indices start at 0, not 1. Why? Because the index is actually an offset (distance from the start):

  • Locker [0] is 0 steps away from the beginning (it is the very first locker).
  • Locker [1] is 1 step away from the beginning (the second locker).
  • If an array has 5 items, their indices are 0, 1, 2, 3, 4.
Working with Arrays
#include <stdio.h>

int main() {
    // An array of 5 integers
    int scores[5] = {95, 88, 72, 99, 84};

    // Reading specific elements
    printf("First score: %d\n", scores[0]); // 95
    printf("Third score: %d\n", scores[2]); // 72

    // Modifying an element
    scores[2] = 78;

    // Looping through all elements to calculate the sum
    int total = 0;
    for (int i = 0; i < 5; i++) {
        total += scores[i];
    }

    printf("Total sum: %d\n", total);
    printf("Average: %.1f\n", (float)total / 5.0f);

    return 0;
}
⚠️ Array Bounds: Never Step Off the Edge!
If an array has 5 items (indices 0 through 4), trying to read or write to scores[10] is called an out-of-bounds access or buffer overflow. In C, this can read arbitrary memory or corrupt other variables. In Rokade, compiling with the -b flag adds automatic runtime checks that halt the program safely if you go out of bounds.
Key Takeaways of Module 10
  • An array stores a fixed-size sequence of elements of the same type in continuous memory.
  • Indices start at 0: an array of size N has valid indices from 0 to N - 1.
  • Combine loops and arrays to process large amounts of data with minimal code.

Module 12: How to Think Like a Programmer

↑ Top

Programming is not about memorizing syntax rules, it is about problem solving and computational thinking. When beginners run into errors or bugs, they often feel frustrated. But in reality, debugging is 80% of what professional software engineers do every day!

12.1 Problem Decomposition: Breaking Big Problems into Tiny Steps

When faced with a complex task (like "build a chess game"), the task feels overwhelming. The secret of programming is decomposition:

  1. Don't try to build the whole thing at once.
  2. Break the problem down into smaller and smaller pieces until each piece is trivial.
  3. Example: "How do I make a chess board?" ➔ "How do I represent 64 squares?" ➔ "How do I represent 1 square?" ➔ "A struct with an X and Y coordinate!"
  4. Solve that one tiny piece, verify that it works, and build the next piece.

12.2 Reading Compiler Errors Without Fear

When the compiler prints a scary red error message, do not panic! The compiler is not angry with you, it is a helpful assistant pointing out where something doesn't make sense:

  1. Look for the file and line number: It will look like src/main.rook:14:5: error. This tells you exactly where the problem occurred (line 14, column 5).
  2. Read the error description: Usually it's something simple, like a missing semicolon ;, an undefined variable name, or passing the wrong type of argument.
  3. Fix only the first error: Often, one typo causes 10 secondary errors below it. Fix the very first error at the top, recompile, and see if the rest disappear!

12.3 Print Debugging: Your Most Reliable Superpower

When a program compiles successfully but does not give the expected answer, the easiest way to find the bug is print debugging. Add printf() statements at critical steps to inspect variable values:

Print Debugging in Practice
int calculate_discount(int price, int customer_years) {
    printf("[DEBUG] Starting calculate_discount: price=%d, years=%d\n", price, customer_years);
    
    int discount = 0;
    if (customer_years > 5) {
        discount = 20;
    }
    printf("[DEBUG] Calculated discount: %d\n", discount);
    
    return price - discount;
}

By watching the printed output, you can see exactly where the computer's logic diverged from what you intended.

12.4 Welcoming Mistakes on Your Journey

Every senior engineer, language designer, and technology creator spent thousands of hours making typos, forgetting semicolons, causing segmentation faults, and troubleshooting compiler errors. Making mistakes is not a sign that you aren't suited for programming,it is the universal mechanism by which every programmer learns. Welcome the challenges, be curious, and have fun building!

Key Takeaways of Module 12
  • Break big problems down into small, easily solvable steps.
  • Read compiler errors from top to bottom, fix the first error first.
  • Use print debugging to inspect variables when programs don't behave as expected.
  • Bugs are normal and natural, treat every error as a fun puzzle to solve.

Module 13: Objects and Methods

↑ Top

As programs grow larger, you often need to bundle data and the operations on that data together. Rook provides two keywords for this: object (to define the data) and impl (to attach methods to it). This idea, sometimes called object-oriented programming, exists in many languages under names like class (Java, Python, C++), struct + impl (Rust), or interface (Go). Not every language has it, but understanding the concept helps you read and write almost any modern codebase.

13.1 Defining an Object

An object in Rook is like a struct, but designed to hold both fields and behaviour. You declare the fields in the object block:

Defining an Object
#include <stdio.h>

object Animal {
    name: const char*
    legs: int
}

13.2 Attaching Methods with impl

An impl block attaches functions (called methods) to the object. Each method receives a pointer to the object as its first argument, named self by convention:

Object with Methods
#include <stdio.h>

object Animal {
    name: const char*
    legs: int
}

impl Animal {
    void speak(Animal* self) {
        printf("%s\n", self.name);
    }
    int legs_count(Animal* self) {
        return self.legs;
    }
}

int main() {
    Animal dog;
    dog.name = "Rex";
    dog.legs = 4;

    // Call methods using the dot operator
    dog.speak();
    printf("Legs: %d\n", dog.legs_count());
    return 0;
}

13.3 Inheritance

One object can extend another using :. The child object gains all the fields and methods of the parent, and can add more of its own:

Inheritance in Rook
object Cat : Animal {
    lives: int
}

impl Cat {
    void meow(Cat* self) {
        self.speak();   // inherited from Animal
    }
}

int main() {
    Cat c;
    c.name = "Tom";
    c.legs = 4;
    c.lives = 9;
    c.speak();
    c.meow();
    printf("Lives left: %d\n", c.lives);
    return 0;
}
Not all languages have this
Object-oriented features like object, impl, and inheritance are powerful tools for organizing large programs. They exist in C++, Java, Python, and Rust (among others), each with different syntax. Some languages (like C and Go) deliberately leave them out and use different organizational patterns instead. Knowing both styles makes you a more flexible programmer.
Key Takeaways of Module 13
  • object defines a custom data type with named fields.
  • impl attaches methods to an object, each receiving a self pointer to the instance.
  • Call methods using the dot operator: dog.speak().
  • Use object Child : Parent to inherit all parent fields and methods.
  • Object-oriented concepts exist in many languages under different names.

Module 14: Pattern Matching

↑ Top

Rook provides a match expression that lets you compare a value against several patterns and run different code for each one. It is similar to a switch statement in C or Java, but more expressive: it can destructure data structures and match on their inner fields in one step. Pattern matching is a feature in Rust, Swift, Haskell, and many functional languages. Not all languages have it, but it is increasingly common in modern language design.

14.1 Basic match on a Value

The simplest use of match is choosing between integer or enum values:

Basic match
#include <stdio.h>

int main() {
    int code = 2;

    match (code) {
        1 => printf("One\n"),
        2 => printf("Two\n"),
        3 => printf("Three\n"),
        _ => printf("Something else\n"),
    }
    return 0;
}

The _ (underscore) is the catch-all pattern, similar to default: in a C switch statement. It matches any value not covered by the earlier arms.

14.2 match on Sum Types (Tagged Unions)

Where match really shines is with sum types (also called tagged unions or variants). A sum in Rook lets a value be one of several possible shapes, and match lets you handle each shape differently:

match on Sum Types
#include <stdio.h>

sum Shape {
    Circle { r: float; };
    Rect   { w: float; h: float; };
    Point;
}

impl Shape {
    float area(Shape* self) {
        return match (*self) {
            Circle { r }    => 3.14159f * r * r,
            Rect   { w, h } => w * h,
            Point           => 0.0f,
            _               => 0.0f,
        };
    }
}

int main() {
    Shape a = Circle { r: 2.0f };
    Shape b = Rect { w: 3.0f, h: 4.0f };
    Shape c = Point;

    printf("Circle area: %f\n", a.area());
    printf("Rect area:   %f\n", b.area());
    printf("Point area:  %f\n", c.area());
    return 0;
}
Not all languages have this
Pattern matching on tagged unions is a hallmark of languages like Rust (enum + match), Swift (enum + switch), and Haskell (data + case expressions). Traditional C only has basic switch on integer values with no destructuring. If you later learn Rust or Swift, you will find these concepts map directly.
Key Takeaways of Module 14
  • match compares a value against patterns and runs the first matching arm.
  • _ is the wildcard catch-all pattern, always placed last.
  • Sum types let a value be one of several distinct shapes, and match handles each shape cleanly.
  • Pattern matching is more expressive than a plain switch because it can unpack inner fields in the same step.
  • This concept exists in Rust, Swift, Haskell, and many modern languages, each with slightly different syntax.
