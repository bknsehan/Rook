The Rook Language Guide

A technical reference manual for Rook, covering syntax, memory semantics, C ABI compatibility, single inheritance, and compiler toolchains.

Compiler: rokade Target audience: Developers with programming experience Offline documentation

1. The Rook Philosophy & Prior Art

Top ↑

C has been the standard language for operating systems, embedded controllers, device drivers, and real-time graphics for decades. Nearly every computing platform exposes a C Application Binary Interface (ABI), making C the universal interface for systems software.

At the same time, developing in C has well-known maintenance challenges and safety pitfalls:

  • Header synchronization: Maintaining declarations in .h files and definitions in .c files requires duplicate maintenance. Inconsistencies between headers and source files lead to linker errors or mismatched symbol definitions.
  • Uninitialized memory defaults: Local variables declared without initializers contain whatever values were left on the stack. Reading them causes undefined behavior.
  • Accidental assignment in conditions: Writing if (x = 5) instead of if (x == 5) compiles silently in standard C, overwriting variables and introducing subtle logic bugs.
  • Boilerplate for common abstractions: Implementing single inheritance or tagged unions in standard C requires nested structs, manual tag checks, and void pointer casting without compiler checks.

Language Trade-Offs and Prior Art

Different languages address these challenges with different design trade-offs:

  • C: Direct hardware mapping, universal ABI compatibility, and zero runtime overhead. However, it lacks module systems, tagged unions, and basic safety guards. Rook preserves C ABI compatibility and compiles directly to standard C, while replacing header files with #comprise, initializing variables to zero by default, and providing single inheritance and sum types.
  • C++: Rich abstractions, generic templates, and extensive standard libraries. However, it introduces complex grammar rules, slow compile times, and symbol name mangling that complicates C interop. Rook retains the straightforward compilation model of C, adding method syntax and defer without virtual tables, mangled symbols, or template overhead.
  • Rust: Compile-time memory safety and concurrency guarantees enforced through a borrow checker. However, it has a steep learning curve and introduces friction when interfacing directly with untyped C memory layouts. Rook uses traditional pointers and explicit memory management, adding targeted compiler checks to prevent common C mistakes without lifetime annotations.
  • Zig and Odin: Clean systems ergonomics, explicit memory allocation, and independent compiler toolchains. However, their standalone ABIs require dedicated bindings to integrate into existing C builds. Rook transpiles to standard C, allowing single .rook files to integrate directly into existing C Makefiles and CMake projects.
  • Go: Fast compilation, simple syntax, and built-in concurrency. However, its garbage-collected runtime makes it unsuitable for bare-metal targets, low-latency audio, or embedded microcontrollers. Rook has no garbage collector, no runtime overhead, and predictable memory layout.

Design Goals

  • 1:1 C ABI compatibility: Functions, structs, and primitive types in Rook match standard C layouts, allowing direct calls to C libraries (such as SDL, Raylib, SQLite, or Vulkan) without wrapper code.
  • Headerless modules: Modules are imported using #comprise, eliminating separate .h files and header guards.
  • Safe defaults: Local variables default to zero initialization, assignments inside conditional expressions are rejected at compile time, and optional bounds checking (-b) checks array access at runtime.
  • Lightweight abstractions: Single inheritance (object Child : Parent), methods (impl), and tagged unions with pattern matching (sum and match) lower to clean, static C code.

Explicit Limitations

  • No borrow checker: Rook does not prove memory lifetimes at compile time. Memory is managed explicitly using pointers, allocators, and arenas.
  • No garbage collector: Memory allocations remain allocated until freed.
  • Early ecosystem: The standard library is small, though direct C interop allows using any existing C library.
  • LLVM backend status: Rokade has two backends: a C transpiler backend and an LLVM backend. The C backend is the primary, production-ready backend. The LLVM backend is experimental and in active development.

Common Use Cases

  • Command-line tools and utilities: Standalone binaries that build quickly and run without runtime dependencies.
  • Game engines and multimedia: Audio, physics, and rendering with Raylib, SDL2, OpenGL, or Vulkan.
  • Upgrading existing C projects: Replacing or adding modules written in type-safe .rook files within existing C codebases.

2.1 Compiler Backends

BackendStatusDescription
C Backend (Default) Primary Transpiles .rook files into formatted C code (C11/C23) and invokes the host C compiler (GCC or Clang) directly. Full C ABI compatibility, standard debugging with GDB or LLDB, and direct inclusion of external C headers. Recommended for regular development.
LLVM Backend Experimental Uses LLVM libraries to generate object files (.o) directly and support in-memory execution (rokade --jit). Supports unsigned operations, pointer arithmetic, sum types, and bounds checks. In active development.

2.2 Compilation Pipeline

  1. Lexing and Parsing: Reads source tokens and builds an Abstract Syntax Tree (AST). The #comprise directive recursively discovers dependencies and deduplicates imports into a single compilation unit.
  2. Semantic Analysis (sema.c): Checks types, validates function argument counts, checks pattern exhaustiveness, enforces pointer rules, and flags prohibited syntax (such as assignments in conditions, division by zero, and goto).
  3. Code Generation:
    • C Backend: Emits formatted C source to build/generated/main.c. Each Rook construct maps to a standard C construct.
    • LLVM Backend: Emits LLVM IR (.ll) and invokes LLVM to produce object files (.o) or run directly in memory via JIT.
  4. Process Execution: Rokade executes the host compiler and linker directly using POSIX fork() and execv() (or CreateProcess on Windows). It avoids shell wrappers (sh -c) to prevent argument escaping problems and injection issues.
Inspecting Generated Code
You can view the C code emitted by Rokade at any time by running rokade --emit-c src/main.rook or inspecting build/generated/main.c.

2.3 C ABI Compatibility

Rook adheres to the host C ABI:

  • Primitives (int, size_t, float, double, char*) have the same sizes, alignments, and calling conventions as C.
  • Rook struct and object types have the same memory layout, field offsets, and padding as C structs.
  • Rook functions can be called directly from C, and C functions can be called directly from Rook without glue code.

3. Direct Comparison: Standard C vs. Rook

Top ↑

This chapter compares standard C patterns with their Rook equivalents.

3.1 Modules and Imports

Standard C requires declaring interfaces in .h header files with include guards, and writing implementations in .c files. Rook uses single-file modules imported with #comprise.

AspectStandard CRook
Source files Dual files: math.h and math.c Single file: math.rook
Import mechanism #include "math.h" with #ifndef guards #comprise math, deduplicated automatically
Signature consistency Header and source must be kept in sync manually Single definition; no duplicate declarations
Standard C: Header and Source
// math.h
#ifndef MATH_H
#define MATH_H
int add(int a, int b);
#endif

// math.c
#include "math.h"
int add(int a, int b) { return a + b; }
Rook: Module Import
// src/math.rook
int add(int a, int b) {
    return a + b;
}

// src/main.rook
#comprise math
#include <stdio.h>

int main() {
    printf("Sum: %d
", add(10, 20));
    return 0;
}

3.2 Variable Initialization

In standard C, uninitialized local variables contain indeterminate stack data. Reading them is undefined behavior. In Rook, uninitialized local variables are automatically set to zero.

DeclarationStandard CRook
Local variable int x; has indeterminate value int x; is initialized to 0 (int x = {0};)
Array int arr[100]; contains uninitialized elements int arr[100]; is zeroed at declaration
Struct Point p; contains uninitialized fields Point p; has all fields zeroed
Standard C (Uninitialized Local)
// Standard C: Undefined behavior
int health; // Uninitialized stack value
if (health > 0) { // Non-deterministic branch
    take_action();
}
Rook (Zero-Initialized)
// Rook: Deterministic initialization
int health; // Initialized to 0
if (health > 0) { // Predictable: branch is not taken
    take_action();
}

3.3 Assignment Inside Conditions

In standard C, accidentally using = instead of == inside an if condition assigns the value and evaluates its truthiness. Rook rejects assignments in conditions at compile time.

Standard C (Silent Mutation)
// Standard C: Compiles silently (or with warning), overwriting status
if (status = 0) {
    handle_success();
}
Rook (Compile Error)
// Rook: Compile-time error
if (status = 0) { // error: assignment used as condition; did you mean '=='?
    handle_success();
}

// Correct:
if (status == 0) {
    handle_success();
}

3.4 Methods and Single Inheritance

Standard C lacks method syntax and inheritance. Structs must be nested manually, and type casting loses safety checks. Rook provides object and impl blocks, lowering to standard C structs without virtual tables.

Standard C: Emulated Inheritance
// Standard C: Manual nesting and casts
typedef struct { float x, y; } Point;
typedef struct { Point base; float radius; } Circle;

void point_move(Point* p, float dx, float dy) { p->x += dx; p->y += dy; }

Circle c = { {10.0f, 20.0f}, 5.0f };
point_move((Point*)&c, 1.0f, 2.0f); // Explicit unverified cast
Rook: Single Inheritance
// Rook: Single inheritance and methods
object Point {
    float x;
    float y;
}

object Circle : Point {
    float radius;
}

impl Point {
    void move(Point* self, float dx, float dy) {
        self.x += dx;
        self.y += dy;
    }
}

Circle c = Circle{ x: 10.0f, y: 20.0f, radius: 5.0f };
c.move(1.0f, 2.0f); // Calls point_move(&c._base, 1.0f, 2.0f)

3.5 Tagged Unions and Pattern Matching

Standard C requires manually synchronizing an enum tag with an untagged union. Rook provides sum types and match expressions.

Rook: Sum Types and Pattern Matching
sum NetworkEvent {
    Connected { int client_id; const char* ip; };
    DataReceived { int client_id; int bytes; };
    Disconnected { int client_id; };
}

void handle_event(NetworkEvent* ev) {
    match (*ev) {
        Connected(c)    => printf("Client %d connected from %s
", c.client_id, c.ip),
        DataReceived(d) => printf("Client %d sent %d bytes
", d.client_id, d.bytes),
        Disconnected(q) => printf("Client %d disconnected
", q.client_id),
    }
}

3.6 Scope Cleanup: goto vs. defer

Cleaning up resources across multiple error exits in C often uses goto cleanup; ladders. Rook provides defer, which executes cleanup statements at scope exit in LIFO order.

Standard C: goto Cleanup
// Standard C: goto cleanup ladder
int process(const char* path) {
    FILE* fp = fopen(path, "r");
    if (!fp) return -1;
    char* buf = malloc(1024);
    if (!buf) { fclose(fp); return -2; }
    
    int ret = 0;
    if (do_work(fp, buf) < 0) { ret = -3; goto cleanup; }
    
cleanup:
    free(buf);
    fclose(fp);
    return ret;
}
Rook: defer Cleanup
// Rook: Scope-based defer cleanup
int process(const char* path) {
    FILE* fp = fopen(path, "r");
    if (!fp) return -1;
    defer fclose(fp); // Runs on any exit path

    char* buf = (char*)malloc(1024);
    if (!buf) return -2;
    defer free(buf); // Runs before fclose(fp)

    if (do_work(fp, buf) < 0) return -3;
    return 0;
}

3.7 Pointer Safety

Standard C allows pointer arithmetic on void* as a compiler extension. Rook rejects arithmetic on void* at compile time, requiring explicit casts to byte-oriented pointers (char* or uint8_t*).

4. Mental Model & Memory Semantics

Top ↑

Rook follows the memory model of standard C: values live on the stack or the heap, pointers represent memory addresses, and data structures have predictable layouts.

4.1 Stack Memory and Zero-Initialization

In standard C, uninitialized local variables contain indeterminate stack data:

Standard C (Uninitialized)
// Standard C: Reading uninitialized stack value
void compute(void) {
    int counter;
    if (ready) counter++; // Undefined behavior
}

In Rook, uninitialized local variables are automatically initialized to zero:

Rook (Zero-Initialized)
int compute() {
    int counter; // Lowered to: int counter = {0};
    printf("%d
", counter); // Prints 0
    return 0;
}

4.2 Heap Allocations and defer

Heap memory in Rook is explicit. Programs allocate memory using functions like malloc, calloc, or custom allocators (such as std/mem arenas). Rook has no garbage collector.

The defer statement ensures resources are released when exiting scope:

Deterministic Scope Cleanup
#include <stdio.h>
#include <stdlib.h>

int process_file(const char* path) {
    FILE* fp = fopen(path, "rb");
    if (!fp) return -1;
    defer fclose(fp); // Guaranteed to execute on function return

    char* buffer = (char*)malloc(4096);
    if (!buffer) return -2;
    defer free(buffer); // Executes before fclose(fp)

    return 0;
}

4.3 Object Memory Layout

Rook's object inheritance embeds the parent type as the first struct member named _base. There are no virtual method tables (vtables), runtime type identifiers, or hidden pointer indirections. A pointer to a derived object is binary-compatible with a pointer to its base type under standard C layout rules.

7. Variables, Types & Invariants

Top ↑

Rook is statically typed. Variables can be declared with inferred types, explicit types, or C-style syntax.

7.1 Variable Declaration Forms

Rook supports three declaration forms:

Variable Declarations
#include <stdio.h>

int main() {
    // 1. Inferred type with 'let'
    let count = 42;             // Inferred as int
    let greeting = "Hello";     // Inferred as const char*

    // 2. Explicit type with 'let'
    let threshold: int = 100;
    let ratio: float = 3.14159f;

    // 3. C-style declaration
    int limit = 500;
    const char* user = "admin";

    printf("%s: count=%d, limit=%d
", greeting, count, limit);
    return 0;
}
Variable Declaration Syntax
Variables must be declared with let (e.g. let x = 10; or let x: int = 10;) or with C-style syntax (int x = 10;). Bare colon declarations without let (such as x: int = 10;) are rejected to prevent ambiguity with labels, conditionals, and struct field definitions.

8. Pointers & Pointer Safety

Top ↑

Pointers in Rook provide direct memory manipulation with compile-time checks that prevent syntax ambiguities and unsafe arithmetic.

8.1 Postfix Pointer Notation

Rook standardizes on postfix notation (Type*):

Pointer Syntax
int* ptr = &x;     // Postfix notation
const char* name;  // Postfix notation
Prefix Pointer Syntax Banned
Prefix notation like *int ptr; is rejected by the parser: 
error: invalid pointer syntax '*Type'; Rook standardizes on postfix 'Type*'

8.2 Pointer Operations

Address-of and Dereference
#include <stdio.h>

void swap(int* a, int* b) {
    int temp = *a;
    *a = *b;
    *b = temp;
}

int main() {
    int x = 10;
    int y = 20;
    swap(&x, &y);
    printf("x=%d, y=%d
", x, y); // x=20, y=10
    return 0;
}

8.3 Pointer Arithmetic Rules

Rook enforces specific rules on pointer calculations:

  • Typed pointer offsets: Adding or subtracting integers from typed pointers (p + 1, p++) steps memory by sizeof(*p) bytes.
  • Prohibition on void* arithmetic: Arithmetic on void* is rejected at compile time. Cast explicitly to byte pointers (char* or uint8_t*):
    void* Arithmetic Check
    void* buf = get_buffer();
// Compile error: pointer arithmetic on 'void*' is invalid
void* next = buf + 8; 

// Correct:
uint8_t* byte_ptr = (uint8_t*)buf;
uint8_t* next_byte = byte_ptr + 8;
  • Prohibition on non-additive operations: Multiplying, dividing, modulo-ing, or bitwise-shifting pointers is rejected at compile time:
    Invalid Pointer Operations
    int* p = &x;
p = p * 2;    // Compile error: invalid operand to binary operator
p = p & 0xFF; // Compile error: invalid operand to binary operator

9. Control Flow & Branching

Top ↑

Rook provides standard control flow constructs with compile-time checks to prevent common logic errors.

9.1 Conditionals: if and else

Conditional Branches
if (status == 200) {
    printf("OK
");
} else if (status >= 400 && status < 500) {
    printf("Client Error
");
} else {
    printf("Other
");
}
Assignment in Condition Banned
Rook's semantic analyzer rejects assignment expressions inside condition blocks:
  • if (cond)
  • while (cond)
  • for (...; cond; ...)
  • switch (cond)
  • Ternary operators: (cond) ? a : b
error: assignment used as condition; did you mean '=='?

9.2 Loops: while, do-while, for, and for-in

Looping Constructs
// 1. while loop
int i = 0;
while (i < 5) {
    i++;
}

// 2. Standard for loop
for (int idx = 0; idx < 10; idx++) {
    if (idx == 3) continue;
    if (idx == 8) break;
}

// 3. for-in loop over array
for score in [95, 88, 72, 100] {
    printf("score: %d
", score);
}

9.3 Scalar Branching: switch

For dispatch on integer and enum values using jump tables, Rook supports standard C switch:

Standard switch
switch (opcode) {
    case 1:
        execute_add();
        break;
    case 2:
        execute_sub();
        break;
    default:
        handle_unknown();
        break;
}
switch and match
The switch statement is intended for scalar values with case labels and explicit break. For pattern matching, destructuring, and sum types, use the match construct (see Chapter 13).

9.4 Prohibition of goto

Rook bans the goto keyword. Control flow must use structured constructs (if, while, for, switch, match, break, continue, and return).

10. Functions & Call Semantics

Top ↑

Functions in Rook follow standard C declaration syntax without extra keywords.

10.1 Function Declarations

Function Definitions
#include <stdio.h>

int multiply(int a, int b) {
    return a * b;
}

void log_message(const char* tag, const char* msg) {
    printf("[%s] %s
", tag, msg);
}

int main() {
    let result = multiply(6, 7);
    log_message("INFO", "Calculation complete");
    return 0;
}

10.2 Compiler Validations

  • Return validation: Non-void functions must return a value across all control paths. A path that reaches the end of the function without returning causes a compile error.
  • Arity and type verification: Function calls are statically verified against declarations. Missing or excess arguments produce compile errors.
  • Scope rules: Functions must be declared at the file level. Nested function definitions are rejected.

10.3 External C Functions (extern)

When calling C functions without including their header file, declare their signature with extern:

extern Declarations
extern int puts(const char* s);
extern void* memcpy(void* dest, const void* src, size_t n);

int main() {
    puts("Direct C linkage");
    return 0;
}

11. Structs & Memory Layout

Top ↑

Structs in Rook represent plain data records that map directly to C struct layout, matching memory alignment, size, and field offsets.

11.1 Definition and Initialization

Fields can be declared using either C-style (Type name;) or let-style (let name: Type;):

Struct Definitions and Initialization
// 1. C-style field definitions
struct Vector2 {
    float x;
    float y;
};

// 2. Let-style field definitions
struct Vector2Let {
    let x: float;
    let y: float;
};

int main() {
    // Positional initialization
    Vector2 v1 = {10.0f, 20.0f};

    // Designated named initialization
    let v2 = Vector2{ y: 50.0f, x: 25.0f };

    printf("v1: (%.1f, %.1f)
", v1.x, v1.y);
    printf("v2: (%.1f, %.1f)
", v2.x, v2.y);
    return 0;
}

11.2 Field Access

Field Access Operators
Vector2 v = Vector2{ x: 1.0f, y: 2.0f };
Vector2* ptr = &v;

// Value field access uses '.'
v.x = 5.0f;

// Pointer field access uses '->'
ptr->y = 10.0f;
Transpilation to Compound Literals
Designated initializers like Vector2{ y: 50.0f, x: 25.0f } transpile directly to C99 designated compound literals: 
((Vector2){.y = 50.0f, .x = 25.0f})

12. Objects, Methods & Single Inheritance

Top ↑

Rook supports single inheritance and method dispatch without virtual method tables (vtables) or runtime type information (RTTI).

12.1 Defining Objects

An object defines a record type that can inherit from another object. Fields support both C-style (Type name;) and let-style (let name: Type;):

Object Inheritance
object Entity {
    int id;
    float x;
    float y;
}

// Player inherits all fields from Entity
object Player : Entity {
    int health;
    const char* username;
}

12.2 Memory Layout

When transpiling object Player : Entity, Rook embeds the base object as the first member named _base:

Generated C Struct
// Generated C representation
typedef struct Entity {
    int id;
    float x;
    float y;
} Entity;

typedef struct Player {
    struct Entity _base; // Embedded at offset 0
    int health;
    const char* username;
} Player;

Because _base is located at offset 0, a pointer to Player can be converted directly to a pointer to Entity under standard C ABI rules.

12.3 Methods with impl

Methods are attached to an object using an impl block:

Methods and Inheritance
#include <stdio.h>

object Shape {
    float x;
    float y;
}

impl Shape {
    void translate(Shape* self, float dx, float dy) {
        self->x += dx;
        self->y += dy;
    }
}

object Circle : Shape {
    float radius;
}

impl Circle {
    void describe(self) { // 'self' infers Circle*
        printf("Circle at (%.1f, %.1f) radius %.1f
", self.x, self.y, self.radius);
    }
}

int main() {
    let c = Circle{ x: 10.0f, y: 15.0f, radius: 5.0f };
    c.describe();

    // Call inherited method
    c.translate(5.0f, -5.0f);
    c.describe();
    return 0;
}
Static Method Dispatch
Method calls like c.describe() lower to direct C function calls: Circle_describe(&c). Inherited calls like c.translate(...) lower to Shape_translate(&c._base, ...). Dispatch is static and resolved at compile time.

13.2 Sum Types (Tagged Unions)

A sum type defines a value that can hold one of several variant shapes. Variant payloads support both C-style (Type name;) and let-style (let name: Type;):

Sum Type Declaration
sum Node {
    Leaf { int value; };
    Branch { Node* left; Node* right; };
    Empty;
}

In memory, Rokade lowers a sum type into a C struct containing an integer discriminator tag and an anonymous union for variant payloads:

Lowered C Tagged Union
typedef struct Node {
    int tag; // Identifies active variant
    union {
        struct { int value; } Leaf;
        struct { struct Node* left; struct Node* right; } Branch;
    };
} Node;

13.3 Pattern Matching with match

The match construct provides destructuring for sum types, enums, and scalar values in both statement and expression forms.

Statement Form:

Statement match
void print_node(Node* n) {
    match (*n) {
        Leaf { value }         => printf("Leaf: %d
", value),
        Branch { left, right } => printf("Branch
"),
        Empty                  => printf("Empty
"),
        _                      => printf("Unknown
")
    }
}

Expression Form:

Expression match
sum Shape {
    Circle { float radius; };
    Rectangle { float width; float height; };
    Point;
}

float calculate_area(Shape s) {
    return match (s) {
        Circle { radius }        => 3.14159f * radius * radius,
        Rectangle { width, height } => width * height,
        Point                    => 0.0f,
        _                        => 0.0f
    };
}

Instantiating Sum Variants

}

int main() {

    Shape b = Rect{ w: 3.0f, h: 4.0f };

19. Safety Invariants & Compile-Time Checks

Top ↑

Rook checks source code at compile time to eliminate common classes of undefined behavior and bugs found in C.

CheckStandard C BehaviorRook BehaviorRationale
Assignment in condition Silently assigns variable and tests truthiness (if (x = 5)). Compile error (including with parentheses: if ((x = 5))) Almost always a typo for == that introduces logic bugs.
Uninitialized locals Contains arbitrary stack data (undefined behavior). Initialized to zero (= 0) Prevents non-deterministic bugs and uninitialized memory reads.
void* pointer arithmetic Compiler extension or undefined behavior. Compile error The size of void is not defined in standard C; cast to char* or uint8_t*.
Invalid pointer operations Permitted in some expressions (e.g. ptr * 2). Compile error Multiplication, division, modulo, and bitwise operations have no meaning on addresses.
Pointer syntax ambiguity Permits multiple formats (int *p, int* p). Enforces postfix (int* p; bans *int p) Ensures consistent parsing.
Division by zero Hardware fault (SIGFPE) or undefined behavior. Compile error for literal zero divisors (e.g. x / 0) Catches obvious zero division at compile time.
Arbitrary jumps (goto) Permitted within function scope. Banned Ensures structured control flow and deterministic cleanup for defer.
Comma operator in expressions Discards first expression and evaluates second. Banned in expression context Reserves commas for argument and element separators.
Include jail violation Allows arbitrary path traversal (e.g. #include "../../../etc/passwd"). Compile error Restricts file inclusion to the project tree, standard library, and dependencies.

Module 1: How Computers Work

Top ↑

Before writing code, it helps to understand how computers run programs and manage data. A computer relies on three main physical components: storage, memory, and the processor.

1.1 Hardware Basics: Storage, RAM, and CPU

Every computer relies on three main components to run software:

Storage (SSD / Hard Drive)
Permanent storage
Holds files when powered off
➔
RAM (Working Memory)
Temporary workspace
Fast access, cleared on shutdown
➔
CPU (Processor)
Calculation engine
Executes instructions sequentially
  • Storage (SSD or Hard Drive): Holds data permanently. When you shut down your computer, your files, operating system, and programs remain intact on disk. Storage has high capacity, but the CPU cannot access it directly at memory speeds.
  • RAM (Random Access Memory): The working memory where active programs run. When you launch a program, the operating system copies it from storage into RAM. The CPU reads and writes RAM in nanoseconds. RAM is volatile: when the computer turns off, all data in RAM is cleared.
  • CPU (Central Processing Unit): The processor that executes program instructions. The CPU fetches an instruction from RAM, executes it (such as adding two numbers or checking a condition), and moves to the next instruction.

1.2 Bits and Bytes: How Hardware Represents Data

At the hardware level, digital circuits store and transmit information using voltages that represent two states: 0 and 1.

  • A single 0 or 1 is called a bit (binary digit).
  • Computers group bits into sets of eight. A group of 8 bits is called a byte.
Why 8 Bits Make a Byte
An 8-bit byte can represent 256 distinct patterns (from 00000000 to 11111111, or 0 through 255 in decimal). Historically, 256 values were sufficient to map every English letter, digit, and punctuation mark in the standard ASCII character set.

1.3 Source Code, Machine Code, and Compilers

Processors only execute machine code: numeric binary instructions tailored to the processor architecture. Because writing machine code directly is impractical, programmers write source code in human-readable text files using languages like Rook or C.

A compiler translates source code into machine code:

  1. Write source code: Instructions saved in a text file (such as main.rook).
  2. Compile the code: The compiler checks syntax, validates types, enforces safety rules, and generates native machine code.
  3. Run the executable: The resulting binary runs directly on the CPU.

1.4 Low-Level and High-Level Languages

Programming languages differ in how closely they expose hardware details:

  • Low-level languages (such as Assembly and C) provide direct control over memory addresses, data layout, and hardware registers. This allows fine-tuned performance, but requires developers to handle memory allocation and types manually.
  • High-level languages (such as Python, JavaScript, and Ruby) abstract away memory management and hardware specifics. They emphasize rapid development, but introduce runtime interpreters or garbage collectors.

Rook bridges these two styles: it retains C-level control and memory layout predictability, while adding compile-time checks that prevent common memory and syntax mistakes.

1.5 Compiled, Interpreted, and Transpiled Languages

Languages take different paths to turn source text into execution:

ApproachHow it worksWhen translation happensExamples
Compiled A compiler translates the entire source program into machine code ahead of time, creating a native binary. Once, before execution C, C++, Rook, Rust, Go
Interpreted An interpreter program reads and executes source instructions line by line at runtime. During program execution Python, Ruby, Bash
Transpiled A source-to-source translator converts code written in one language into another high-level language, which is then compiled or interpreted. Before compilation or execution TypeScript (to JS), Rook C-backend (to C)
Where Rook Fits
Rook is a compiled systems language. The rokade compiler translates Rook source code into clean C code (default backend) or LLVM IR (LLVM backend), which is then compiled into a standalone native executable. It requires no virtual machine or runtime interpreter.
Summary of Module 1
  • Storage holds files permanently, RAM provides fast working memory, and the CPU executes instructions.
  • Digital data is stored as bits (0 and 1) grouped into 8-bit bytes.
  • Source code is human-readable text; compilers convert it into machine code for the CPU.
  • Compiled programs run as native binaries without requiring a runtime interpreter.

Top ↑

Programs store data in variables. A variable is a named location in memory that holds a value of a specific data type.

3.1 Understanding Variables

A variable has three key properties:

  • Name (Identifier): How you reference the variable in code (such as health or count).
  • Type: The kind of data it stores, determining how much memory it uses and which operations are valid.
  • Value: The current data stored in that memory location.

Module 4: Doing Math & Making Comparisons

Top ↑

Programs compute results and evaluate conditions using operators.

4.1 Arithmetic Operators

  • + (Addition): 10 + 5 evaluates to 15
  • - (Subtraction): 10 - 5 evaluates to 5
  • * (Multiplication): 10 * 5 evaluates to 50
  • / (Division): 10 / 5 evaluates to 2
  • % (Modulo / Remainder): 10 % 3 evaluates to 1
Integer Division
Dividing two integers performs integer division, which truncates the fractional portion. For example, 7 / 2 evaluates to 3. To obtain a decimal result, use floating-point numbers: 7.0f / 2.0f evaluates to 3.5f.

4.2 Comparison Operators

Comparison operators compare two values and produce a boolean result (true or false):

  • == (Equal to): checks if two values are equal. Note that == compares values, while = assigns them.
  • != (Not equal to): checks if two values differ.
  • > and <: greater than, less than.
  • >= and <=: greater than or equal, less than or equal.

4.3 Logical Operators

  • && (Logical AND): true only if both operands are true.
  • || (Logical OR): true if at least one operand is true.
  • ! (Logical NOT): inverts a boolean value (e.g. !true is false).
Operators in Action
#include <stdio.h>

int main() {
    int age = 20;
    bool has_id = true;

    if (age >= 18 && has_id) {
        printf("Admission granted.
");
    }

    int items = 14;
    int pack_size = 4;
    int leftover = items % pack_size;
    printf("Remaining items: %d
", leftover); // Prints 2

    return 0;
}
Summary of Module 4
  • Use == to compare values, and = to assign values.
  • Integer division discards remainders; use floating-point numbers when decimal precision is needed.
  • Combine conditions using && (AND), || (OR), and ! (NOT).

Module 5: Making Choices: Control Flow

Top ↑

Control flow structures allow programs to execute different code blocks based on conditions.

5.1 The if, else if, and else Construct

An if statement evaluates a condition. If the condition is true, the corresponding block executes; otherwise, execution continues to the next branch.

Branching Evaluation
#include <stdio.h>

int main() {
    int score = 85;

    if (score >= 90) {
        printf("Grade: A
");
    } else if (score >= 80) {
        printf("Grade: B
");
    } else if (score >= 70) {
        printf("Grade: C
");
    } else {
        printf("Grade: F
");
    }

    return 0;
}

Evaluation steps:

  1. The program checks score >= 90. Because 85 is less than 90, it proceeds to the next check.
  2. It checks score >= 80. This is true.
  3. The program prints Grade: B and skips the remaining branches.

5.2 Compile-Time Enforcement: Assignments in Conditions

In standard C, accidentally writing if (score = 100) instead of if (score == 100) assigns 100 to score and treats the result as true. Rook checks condition expressions at compile time and rejects assignments inside conditions:

Compile Error on Assignment in Condition
// Compile error in Rook:
// error: assignment used as condition; did you mean '=='?
if (score = 100) {
    printf("Perfect
");
}
Summary of Module 5
  • Use if and else if to branch based on conditions.
  • Only the first matching branch in an if/else if chain is executed.
  • Assignments inside conditional expressions are compile-time errors in Rook.

Module 6: Repetition: Automating with Loops

Top ↑

Loops repeat a block of code as long as a condition is met, or across a specific count.

6.1 The while Loop

A while loop continues executing its body as long as the condition remains true:

Countdown with while
#include <stdio.h>

int main() {
    int countdown = 5;

    while (countdown > 0) {
        printf("%d...
", countdown);
        countdown = countdown - 1;
    }

    printf("Done.
");
    return 0;
}
Infinite Loops
If the loop condition never becomes false (for example, if countdown is not decremented), the loop will run indefinitely. Ensure that the loop body makes progress toward terminating the condition.

6.2 The for Loop

When iterating a specific number of times, a for loop groups the initialization, condition, and step in one place:

Counting with for
#include <stdio.h>

int main() {
    for (int i = 1; i <= 5; i++) {
        printf("Iteration: %d
", i);
    }
    return 0;
}
  • int i = 1;: initializes the loop counter once at the start.
  • i <= 5;: checked before each iteration. When false, the loop ends.
  • i++: increments the counter after each iteration.

6.3 Loop Control: break and continue

  • break exits the enclosing loop immediately.
  • continue skips the rest of the current iteration and begins the next cycle.
Summary of Module 6
  • Use while when the number of iterations depends on runtime state.
  • Use for when counting or iterating a known number of steps.
  • Use break to exit early and continue to skip to the next iteration.

Module 7: Functions: Reusable Building Blocks

Top ↑

Functions organize code into named, modular units that take inputs, perform computations, and return results.

7.1 Function Structure

A function definition specifies its return type, name, parameters, and body:

Defining and Calling Functions
#include <stdio.h>

// Takes two integers, returns their sum
int add(int a, int b) {
    return a + b;
}

// Takes a string, returns nothing (void)
void greet(const char* name) {
    printf("Hello, %s!
", name);
}

int main() {
    greet("Alice");
    greet("Bob");

    int sum = add(15, 25);
    printf("15 + 25 = %d
", sum);

    return 0;
}

7.2 Variable Scope

Variables declared inside a function are local to that function. They are created when the function executes and discarded when it returns. Functions cannot directly read or modify local variables defined in other functions.

Summary of Module 7
  • Functions divide logic into named, reusable components.
  • Parameters receive input arguments; the return statement sends back a result.
  • Functions that return no value use the void return type.
  • Local variables are scoped to the function in which they are declared.

Module 8: Grouping Data: Structures

Top ↑

A struct (structure) groups related variables under a single custom data type.

8.1 Defining and Instantiating a Struct

In Rook, fields can be declared using either C style (Type name;) or let style (let name: Type;):

Struct Definition and Field Access
#include <stdio.h>

// C-style field definitions
struct Player {
    const char* name;
    int health;
    int score;
};

// Equivalent let-style field definitions
struct PlayerLet {
    let name: const char*;
    let health: int;
    let score: int;
};

int main() {
    // Initializing with named fields
    Player hero = Player{
        name: "Arthur",
        health: 100,
        score: 0
    };

    // Accessing fields with dot notation
    printf("Player: %s
", hero.name);
    printf("Health: %d HP
", hero.health);

    // Updating a field
    hero.score += 500;
    printf("Updated Score: %d
", hero.score);

    return 0;
}
Summary of Module 8
  • Structs bundle multiple related variables into a single record.
  • Field declarations support both C-style (Type name;) and let-style (let name: Type;).
  • Fields are accessed and modified using the dot operator (hero.health).

Module 9: Demystifying Memory: Pointers

Top ↑

In systems programming, programs interact directly with computer memory. A pointer is a variable that stores the memory address of another value.

9.1 Addresses and Pointers

Every variable resides at a distinct location in RAM, identified by its memory address:

  • The variable holds the actual data value.
  • The pointer holds the numerical memory address where that variable is located.

9.2 The Address-Of (&) and Dereference (*) Operators

  • & (Address-of): returns the memory address of a variable (e.g. &x).
  • * (Dereference): accesses the value stored at the address a pointer holds (e.g. *ptr).
Pointers and Dereferencing
#include <stdio.h>

int main() {
    int value = 42;
    int* ptr = &value; // ptr stores the address of value

    printf("Value: %d
", value);
    printf("Address: %p
", (void*)ptr);

    // Modify value through the pointer
    *ptr = 100;
    printf("New Value: %d
", value); // Prints 100

    return 0;
}

9.3 Common Uses for Pointers

  • Modifying values across function calls: When arguments are passed by value, the function receives a copy. Passing a pointer allows a function to update the caller's original data.
  • Passing large structures efficiently: Passing a pointer copies an 8-byte memory address rather than duplicating entire structs in memory.

9.4 Null Pointers

A pointer with an address of 0 is called a null pointer. It indicates that the pointer does not reference valid memory. Attempting to dereference a null pointer causes an immediate operating system crash (segmentation fault). Check pointers before dereferencing when an address may be absent.

Summary of Module 9
  • A pointer stores the memory address of another variable.
  • Use & to get a variable's address, and * to access the value at that address.
  • Pointers allow functions to mutate caller values and avoid copying large data structures.
  • Dereferencing a null pointer causes a segmentation fault.

Module 10: Working with Lists: Arrays

Top ↑

An array stores a fixed-size sequence of elements of the same data type in contiguous memory.

10.1 Declaring and Indexing Arrays

Array indices in Rook and C are zero-based, representing an offset from the start of the array:

Array Declaration and Indexing
#include <stdio.h>

int main() {
    int scores[5] = {95, 88, 72, 99, 84};

    // Reading elements by index
    printf("First: %d
", scores[0]); // Index 0
    printf("Third: %d
", scores[2]); // Index 2

    // Modifying an element
    scores[2] = 78;

    // Summing elements with a loop
    int total = 0;
    for (int i = 0; i < 5; i++) {
        total += scores[i];
    }

    printf("Total: %d
", total);
    printf("Average: %.1f
", (float)total / 5.0f);

    return 0;
}
Array Bounds
An array with 5 elements has valid indices from 0 to 4. Accessing scores[5] or higher is out of bounds. In standard C, out-of-bounds access reads or overwrites adjacent memory. In Rokade, compiling with the -b flag enables runtime bounds checking that stops execution if an index is out of range.
Summary of Module 10
  • Arrays hold a fixed number of elements of the same type stored contiguously.
  • Indices start at 0 and end at length - 1.
  • Use the -b compiler flag to detect out-of-bounds errors at runtime.

Module 11: Building Real Projects

Top ↑

As applications grow, organizing code across multiple files becomes essential for maintainability.

11.1 Project Structure

Running rokade new my_project creates a standardized project directory:

Project Directory Layout
my_project/
├── rokade.toml          # Project configuration, name, version, and dependencies
├── src/
│   ├── main.rook        # Application entry point containing main()
│   └── math_utils.rook  # Utility functions module
└── build/               # Generated binaries and intermediate files

11.2 Importing Modules with #comprise

In standard C, splitting code across files requires creating .h header files with include guards. Rook replaces this with the #comprise directive:

Modular Multi-File Code
// src/math_utils.rook
int square(int x) {
    return x * x;
}

// src/main.rook
#comprise math_utils
#include <stdio.h>

int main() {
    int val = 8;
    printf("%d squared is %d
", val, square(val));
    return 0;
}

When Rokade builds the project, it parses math_utils.rook, verifies types, and compiles both modules into a single binary without duplicate symbol errors.

Summary of Module 11
  • Organize code into separate files by function or module.
  • rokade.toml configures project settings and dependencies.
  • Use #comprise filename to import local Rook source files directly without header files.

Module 12: How to Think Like a Programmer

Top ↑

Programming centers on problem solving: decomposing tasks into small, verifiable steps and locating errors methodically.

12.1 Problem Decomposition

When solving an unfamiliar problem, avoid writing everything at once:

  1. Break the task into smaller subtasks until each subtask has a straightforward solution.
  2. Write and verify each component independently.
  3. Compose the tested components into the complete solution.

12.2 Reading Compiler Errors

Compiler errors provide actionable diagnostics when code violates syntax or type rules:

  1. Check the file and line number: An error like src/main.rook:14:5: error points to line 14, column 5.
  2. Read the error description: Common errors include missing semicolons, unrecognized identifiers, or type mismatches.
  3. Fix the top error first: A single error near the top of a file can trigger several downstream warnings. Address the first error and recompile.

12.3 Print Debugging

When a program compiles but produces unexpected output, adding printf statements lets you inspect values as execution proceeds:

Tracing Values with printf
int calculate_discount(int price, int customer_years) {
    printf("[DEBUG] price=%d, years=%d
", price, customer_years);
    
    int discount = 0;
    if (customer_years > 5) {
        discount = 20;
    }
    printf("[DEBUG] calculated discount=%d
", discount);
    
    return price - discount;
}

Examining intermediate outputs clarifies where execution diverges from expectations.

Summary of Module 12
  • Decompose complex requirements into small, testable steps.
  • Read compiler messages carefully, starting with the first reported error.
  • Trace program state with print statements to diagnose logic errors.

Module 13: Objects and Methods

Top ↑

In addition to plain structs, Rook provides object and impl for organizing state and associated methods together. This model supports single inheritance with static dispatch.

13.1 Defining an Object

An object defines data fields. Fields support both C-style (Type name;) and let-style (let name: Type;):

Defining an Object
#include <stdio.h>

object Animal {
    const char* name;
    int legs;
}

13.2 Attaching Methods with impl

Methods are defined in an impl block. Each method takes a pointer to the instance as its first argument, conventionally named self:

Attaching Methods to Objects
#include <stdio.h>

object Animal {
    const char* name;
    int legs;
}

impl Animal {
    void speak(Animal* self) {
        printf("%s
", self.name);
    }
    int legs_count(Animal* self) {
        return self.legs;
    }
}

int main() {
    Animal dog;
    dog.name = "Rex";
    dog.legs = 4;

    dog.speak();
    printf("Legs: %d
", dog.legs_count());
    return 0;
}

13.3 Single Inheritance

An object can extend a base object using a colon (:). The child object inherits the parent object's fields and methods:

Single Inheritance
object Cat : Animal {
    int lives;
}

impl Cat {
    void meow(Cat* self) {
        self.speak(); // Calls inherited Animal.speak
    }
}

int main() {
    Cat c;
    c.name = "Tom";
    c.legs = 4;
    c.lives = 9;

    c.speak();
    c.meow();
    printf("Lives: %d
", c.lives);
    return 0;
}
Language Comparison
Object-oriented concepts appear across many languages. C++, Java, and Python use classes with methods. Rust uses structs with impl blocks. Other languages, like C and Go, avoid class inheritance in favor of composition or interface tables. Rook provides single inheritance lowered statically to nested C structs with zero vtable overhead.
Summary of Module 13
  • object defines records with named fields in C-style or let-style.
  • impl binds methods to an object, taking an explicit self pointer.
  • object Child : Parent establishes single inheritance.
  • Method dispatch is static and maps directly to C function calls without virtual tables.

Module 14: Pattern Matching

Top ↑

Rook provides a match construct that compares values against patterns and executes the matching arm. It supports scalar values, enums, and sum types (tagged unions).

14.1 Value Matching

The simplest form matches integers or enums against constant patterns:

Basic Pattern Match
#include <stdio.h>

int main() {
    int code = 2;

    match (code) {
        1 => printf("One
"),
        2 => printf("Two
"),
        3 => printf("Three
"),
        _ => printf("Other
"),
    }
    return 0;
}

The underscore _ acts as a wildcard pattern that matches any value not matched by prior arms.

14.2 Pattern Matching on Sum Types

A sum type represents a value that can hold one of several variant shapes. A match expression inspects the variant and destructures its payload fields:

Matching on Sum Types
#include <stdio.h>

sum Shape {
    Circle { float r; };
    Rect   { float w; float h; };
    Point;
}

impl Shape {
    float area(Shape* self) {
        return match (*self) {
            Circle { r }    => 3.14159f * r * r,
            Rect   { w, h } => w * h,
            Point           => 0.0f,
            _               => 0.0f,
        };
    }
}

int main() {
    Shape a = Circle { r: 2.0f };
    Shape b = Rect { w: 3.0f, h: 4.0f };
    Shape c = Point;

    printf("Circle area: %f
", a.area());
    printf("Rect area:   %f
", b.area());
    printf("Point area:  %f
", c.area());
    return 0;
}
Language Comparison
Pattern matching on tagged unions is common in languages like Rust, Swift, and Haskell. Traditional C offers switch on integers without payload destructuring, requiring manual union tagging. Rook provides tagged unions and pattern matching directly in the grammar.
Summary of Module 14
  • match compares values against patterns and executes the first matching arm.
  • The _ pattern serves as the fallback arm.
  • Sum types represent values that can take one of multiple variant shapes.
  • Pattern matching destructures sum type variant payloads in a single step.
